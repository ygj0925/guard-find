`mvn -pl guard-find-server-system test -Dtests.skip=false` → **Tests run: 35, Failures: 6, Errors: 17**

失败原因分两类:

### 5.2 响应码类型已修正并实测(2026-09-25 第二轮)

结论:**错的是契约,不是框架**。同一工作区的管理端 `guard-find-frontend/src/utils/RequestConfig.ts:42` 写的就是 `const SUCCESS_CODE = '0'`(字符串),框架 `top.continew.starter.web.model.R#code` 本身就是 `String`。

实测温到的框架映射(`common/config/exception/`):`BusinessException→"500"`、`BadRequestException→"400"`、`NotLoginException→"401"`、`NotPermissionException→"403"`、成功 `"0"`。因此:

1. **契约已重写**:§0 明确 `code` 为字符串、客户端 MUST 用 `String(code)==='0'` 判定;错误码表拆成"框架层"(0/400/401/403/405/500)与"业务层"(4002/4003/4005/4006/4290),并如实记录"对外不可见的档案返回 `code="500"`+`msg`,不是 404"。
2. **后端补齐业务层码通道**:新增 `app/exception/AppBizException`(携带字符串码)与 `AppExceptionHandler`(`@Order(98)`,只处理该异常,不动既有两个 advice)。`AppUserContextHolder.getUserIdRequired()` 原先抛 `BusinessException` → 会被框架塌成 `"500"`,客户端"清会话+跳登录"永远不触发;改抛携带 `"401"` 的业务异常。
3. **前端致命 bug 已修**:`client.ts` 原本 `typeof envelope?.code === 'number' ? envelope.code : response.status`,在字符串码下会把所有**成功**响应退化为 HTTP 200 判成失败。改为 `Number()` 归一并保留数字兼容。`ApiCode` 取值按实测重写(校验 4001→400、服务器异常 1→500,补 405)。
4. **新增 7 个回归用例** `lib/api/__tests__/client-test.ts`:字符串 `"0"` 判成功、数字 0 兼容、`"401"` 归一且并发只触发一次登出、`"4005"`/`"4290"` 可识别(含 retryAfter 解析)、`"400"` 不当未知错误、非信封 HTML 不静默成功。`pnpm test:ci` → **7 passed**;`pnpm typecheck` → **0 error**。

## 6. 第三轮:采集缺陷修复与单测根因改判(2026-09-25)

### 6.1 采集链路两处真实缺陷已修

`CandidateMapperTest` 由 2 失败转为 **9/9 通过**。两处都是生产缺陷,不是测试写法问题:

1. `XunrenHtmlParser.parseListPageUrls` 用 `ReUtil.isMatch` 判 href(整串匹配),而传入
   baseUri 后 `link.attr("href")` 已是绝对地址 → 每个条目都被跳过,**列表恒为空**。
   这条同时打死真实采集:`rangaihuijia` 也一条都采不到。
2. `RegionMatcher.match` 要求先命中省份,否则区划全空。源站"失踪地址"大量只写到市
   → 同一人裂成两条候选,**去重失效**。改为省未命中时取唯一市级命中回推省码,
   多义则放弃推断(绝不猜)。

附带把 `CaseDedupeKeyUtil.normalizeName` 的全角折叠补回 —— 那是我自己早先为绕开
"当前 Hutool 版本没有 toDBC"而引入的回归。提交 `8aec3bd`。

### 6.2 剩余 21 例的根因改判(推翻我上一轮的说法)

我先前判断"是测试把 Mockito 静态打桩写错了",**不准确**。实跑报错是:

```
NoClassDefFound: Could not initialize class
  top.continew.starter.core.util.validation.ValidationUtils
Mockito cannot instrument ... RedisUtils because it or one of its supertypes
  could not be initialized
```

即 ContiNew 的 `ValidationUtils` / `RedisUtils` 带依赖容器就绪的静态初始化,在不起
Spring 上下文的纯单测里**根本无法加载**;生产代码直接调这两个静态工具,等于自身不可
纯单测。所以这不是测试写法能修的,需要二选一:

- 为缓存与校验引入可注入的薄封装(seam),测试打桩封装 —— 改动可控、可长期复用;
- 或让测试带最小容器上下文 —— 会连带要求 MySQL/Redis,违背"无外部依赖跑单测"的约定。

当前：`Tests run: 35, Failures: 4, Errors: 17`。4 个断言失败需在 seam 落地后逐个判定
