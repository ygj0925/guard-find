# Guard Find 项目结构说明

> 审阅范围：`guard-find-app`、`guard-find-server`、`guard-find-frontend`、`guard-find-backend`。  
> 审阅方式：静态代码与配置审阅；未执行安装、构建、测试、数据库迁移或容器部署。  
> 更新日期：2026-08-20。

## 1. 工作区总览

本仓库采用四项目并列的形态，按客户端与后台管理两条业务链划分：

```text
Guard Find 工作区
├─ guard-find-app       面向用户的移动端 / Web 端应用
├─ guard-find-server    面向用户应用的服务端
├─ guard-find-frontend  管理后台 Web 前端
└─ guard-find-backend   管理后台服务端
```

建议的逻辑调用关系如下：

```text
┌───────────────────────────────────────┐
│ guard-find-app                        │
│ Expo + React Native：Android/iOS/Web/ │
│ HarmonyOS                             │
└────────────────┬──────────────────────┘
                 │ 用户侧 REST / WebSocket API（待按业务定义）
┌────────────────▼──────────────────────┐
│ guard-find-server                     │
│ Spring Boot：用户侧业务服务、认证、     │
│ 数据与领域能力                         │
└───────────────────────────────────────┘

┌───────────────────────────────────────┐
│ guard-find-frontend                   │
│ Umi Max + React：后台运营管理页面       │
└────────────────┬──────────────────────┘
                 │ /dev-api（开发代理）或生产 API 前缀
┌────────────────▼──────────────────────┐
│ guard-find-backend                    │
│ Spring Boot：后台管理、租户、权限、     │
│ 系统配置与运营能力                      │
└───────────────────────────────────────┘
```

目前两个 Java 服务端的代码结构都以 **ContiNew Admin 4.2.0-SNAPSHOT** 脚手架为基础，且未检索到 Guard Find 专属的领域实体、接口、服务或数据库迁移。它们具备通用中后台能力，但仍需要根据用户侧和后台侧的实际业务边界补充专属模块，并明确两个服务的职责是否需要长期独立。

## 2. 项目职责与技术栈

| 项目 | 定位 | 主要技术栈 | 主要运行端口/入口 |
| --- | --- | --- | --- |
| `guard-find-app` | 用户应用；兼顾移动端与网页端 | Expo SDK 52、React 18、React Native 0.77、Expo Router、React Native Web、RNOH | Expo Router 入口；Web/Android/iOS/HarmonyOS |
| `guard-find-server` | 用户应用对应服务端 | Java 17、Spring Boot 3.3、MyBatis-Plus、Sa-Token、Redis、MySQL、Liquibase | `ContiNewAdminApplication`；dev 默认 `8000` |

## 3. guard-find-app：用户应用（移动端 + Web）

### 3.1 当前定位

`guard-find-app` 是一个采用 Expo 管理工作流的 React Native 项目，已配置 Android、iOS、Web 和 HarmonyOS 的基础适配。当前应用层仍接近 Expo Router 模板：只有 Home 与 Explore 示例页面，尚未建立真实业务页面、网络请求层、认证状态、数据模型或与 `guard-find-server` 的接口调用。

### 3.2 关键目录

```text
guard-find-app/
├─ app/                         Expo Router 文件系统路由
│  ├─ _layout.tsx               根布局：主题、Stack、StatusBar
│  ├─ +not-found.tsx            未匹配路由页面
│  └─ (tabs)/
│     ├─ _layout.tsx            Home / Explore 底部 Tab 定义
│     ├─ index.tsx              Home 模板页
│     └─ explore.tsx            Explore 模板页
├─ components/                  可复用 UI 组件
│  ├─ ui/                       图标、Tab 背景等基础组件
│  └─ __tests__/                ThemedText 快照测试
├─ hooks/                       主题与颜色相关 Hook
├─ constants/Colors.ts          浅色/深色主题色板
├─ assets/                      图片、图标、字体等静态资源
├─ scripts/                     HarmonyOS 启动、打包、安装后处理脚本
├─ shims/                       HarmonyOS 下 Expo 能力的兼容实现
├─ patches/                     RNOH/Expo 依赖补丁
├─ docs/                        HarmonyOS 使用、补丁、排障说明
├─ metro.config.js              Metro 与 HarmonyOS 分平台解析配置
├─ index.harmony.js             HarmonyOS 专用应用初始化入口
├─ app.json                     Expo、Web、Android、HarmonyOS 元数据
└─ package.json                 依赖与脚本
```

### 3.3 页面与共享 UI

- `app/_layout.tsx`：使用 `ThemeProvider` 注入系统主题；注册 `(tabs)` 与 `+not-found` 路由；初始化 Reanimated。
- `app/(tabs)/_layout.tsx`：当前仅配置 `index`（Home）和 `explore`（Explore）两个 Tab。
- `components/ThemedText.tsx`、`components/ThemedView.tsx`：主题感知的基础文本与容器。
- `components/ParallaxScrollView.tsx`：使用 Reanimated 实现带头图的滚动视图。
- `hooks/useColorScheme.web.ts`：为 Web 静态输出后的客户端 hydration 提供主题兼容处理。

### 3.4 多端适配现状

| 平台 | 当前状态 | 关键位置 |
| --- | --- | --- |
| Web | 已配置 `react-native-web`、Metro 静态输出与 favicon；暂无 Web 专属业务布局 | `app.json`、`hooks/useColorScheme.web.ts` |

| HarmonyOS | 已接入 RNOH 和 Expo Harmony CLI，需要生成 `harmony/` 原生工程 | `metro.config.js`、`index.harmony.js`、`scripts/`、`shims/`、`patches/` |

## 4. guard-find-server：用户应用服务端

### 4.1 当前定位

该项目是 Java 多模块服务端，当前为 ContiNew Admin 通用中后台能力集合。其预期定位是为用户应用提供后端服务，但现有代码的可见能力仍以认证、RBAC、系统管理、租户、文件、消息与调度为主；尚未发现 Guard Find 用户侧特有领域模块。

### 4.2 模块结构

```text
guard-find-server/
├─ continew-server/                     主 API 与可部署服务模块
│  ├─ src/main/java/.../ContiNewAdminApplication.java
│  ├─ src/main/java/.../config/         Sa-Token、日志、全局配置等
│  └─ src/main/resources/
│     ├─ config/                         application.yml、dev/prod 配置
│     └─ db/changelog/                   Liquibase 主迁移清单
├─ continew-system/                     认证与系统管理业务
│  ├─ auth/                              登录、用户上下文、动态路由
│  └─ system/                            用户、角色、菜单、组织、文件等
├─ continew-common/                     跨模块基础设施与 CRUD 基类
├─ continew-plugin/                     可随主服务装配的插件聚合
│  ├─ continew-plugin-open/              开放平台与请求签名
│  ├─ continew-plugin-tenant/            租户与套餐
│  ├─ continew-plugin-schedule/          SnailJob 调度客户端
│  └─ continew-plugin-generator/         代码生成
├─ continew-extension/
│  └─ continew-extension-schedule-server/ 独立 SnailJob 调度服务
├─ docker/                              Dockerfile 与 Compose 编排
├─ .github/workflows/                   构建、部署、扫描、发版工作流
└─ pom.xml                              Maven reactor 根配置
```

### 4.3 请求与业务分层

```text
HTTP 请求
  → Sa-Token 拦截器 / Open API 签名校验
  → Controller（标准接口或 @CrudRequestMapping）
  → Service / BaseServiceImpl
  → Mapper / Mapper XML / MyBatis-Plus
  → MySQL

辅助基础设施：Redis（缓存、会话、验证码等） / Liquibase / 文件存储 / SnailJob
```

- 主应用入口：`continew-server/src/main/java/top/continew/admin/ContiNewAdminApplication.java`。
- 认证入口：`AuthController` 与 `AuthServiceImpl`。登录通过 `LoginHandlerFactory` 按认证方式选择处理器，完成客户端校验、用户校验、Sa-Token 登录和动态菜单生成。
- 权限模型：用户—角色—菜单/按钮权限码；通用 CRUD 控制器会按资源路径和操作推导权限，例如 `system:user:create`。
- 数据模型：业务模块通常将 `entity`、`req`、`query`、`resp` 分开，避免直接暴露数据库实体。
- 多租户：采用行级隔离，使用 `X-Tenant-Id` 或 `X-Tenant-Code`；部分系统配置类表不参与租户条件过滤。

### 4.4 环境与启动

```powershell
# 需要先准备 MySQL 与 Redis，并配置 DB_*、REDIS_* 等环境变量
mvn compile
mvn package

# 或直接在 IDE 运行
# top.continew.admin.ContiNewAdminApplication
```

- 默认 Profile：`dev`；主服务端口：`8000`。
- 生产 Profile：`prod`；主服务端口：`18000`。
- 默认输出为 thin jar，可使用 Maven `fat-jar` profile 改为 Spring Boot 可执行胖包。
- `docker/docker-compose.yml` 包含 MySQL、Redis、Nginx、主服务和 SnailJob 调度服务的部署拓扑。

### 4.5 服务端注意事项

- 需要将现有通用模块与用户侧领域模块分离，例如新增独立的 `guardfind-*` 或同等清晰的业务包，配套数据库迁移、权限项、接口文档和测试。
- 配置中包含开发默认连接信息、加密参数与签名类配置。真实环境必须使用环境变量或密钥管理服务覆盖，不能沿用示例值。
- 当前默认 MySQL 路径最完整；PostgreSQL 相关配置/脚本处于候选或注释状态，迁移数据库需要整体验证。
- Maven 根配置默认跳过 Surefire 测试，且可见测试很少；构建并不代表核心认证、租户隔离或迁移逻辑已被验证。
- SnailJob 的 Compose 端口、主机名与应用配置需在实际容器网络中联调确认后再启用生产调度。

## 5. guard-find-frontend：管理后台前端

### 5.1 当前定位

管理后台采用 Umi Max + Ant Design Pro 风格的动态路由架构。后端下发用户可见菜单，前端将菜单 `component` 字段映射到页面的懒加载模块，再注入客户端路由；因此后台菜单数据、页面文件路径和页面映射生成结果之间存在严格契约。

### 5.2 关键目录

```text
guard-find-frontend/
├─ src/
│  ├─ app.tsx                         Umi 运行时入口、初始化、请求与路由钩子
│  ├─ access.ts                       基于角色与权限码的访问控制
│  ├─ layouts/                        后台壳、菜单、标签页、KeepAlive 等
│  ├─ pages/                          业务页面，按领域拆分
│  ├─ services/                       Web API、Swagger 与模板服务层
│  ├─ models/                         Umi Hook Model 状态
│  ├─ components/                     字典、组织树、编辑器、权限等通用组件
│  ├─ utils/                          请求、存储、认证、加密、动态路由
│  ├─ locales/                        国际化资源
│  └─ global.css / global.less        全局样式
├─ config/
│  ├─ config.ts                       Umi 主配置
│  ├─ config.dev.ts                   开发环境与代理配置
│  ├─ config.prod.ts                  生产环境编译常量
│  └─ routes.ts                       静态认证与异常路由
├─ scripts/genPageMap.js              扫描页面并生成动态导入映射
├─ docs/menu-config.sql               后台菜单与页面 component 字段示例
├─ public/                            favicon、加载脚本、CNAME 等静态资源
├─ tests/                             Jest 环境初始化
├─ .husky/                            Git 提交钩子
└─ package.json
```

### 5.3 启动、认证与动态路由流程

```text
浏览器打开应用
  → src/app.tsx#getInitialState 恢复本地 token 和用户信息
  → 请求 /auth/user/info 与 /auth/user/route
  → RouteUtils 将菜单树转换为 ProLayout 菜单
  → pageImports 映射 component 到 React.lazy 页面
  → patchClientRoutes 注入业务路由
  → BaseLayouts 提供菜单、权限、多标签页、保活与登录守卫
```

- `src/utils/RequestConfig.ts`：拼接 API 前缀，注入 `Authorization: Bearer <token>` 和 `X-Tenant-Id`，处理业务响应与 401 登出。
- `src/pages/user/auth-login.tsx`：提供账号密码、手机验证码、邮箱验证码及 SSO/企业登录入口；账号密码会先进行 RSA 加密。
- `src/layouts/BaseLayouts.tsx`：负责未登录跳转、密码过期跳转、动态菜单、字典、水印、多标签页、KeepAlive、通知等后台公共体验。
- `src/services/web/`：接口按登录、系统、租户、调度、日志、通知、开放平台、代码生成、文件、短信等领域拆分。

### 5.4 常用命令

```powershell
npm install

# 推荐开发模式：生成页面映射并使用开发环境
npm run start:dev

# 目标组织构建
npm run build:zy
npm run build:gj

# 质量检查
npm run tsc
npm run lint
npm run test
npm run test:coverage
```

开发环境会把 `/dev-api/*` 代理至 `http://localhost:8000` 并移除 `/dev-api` 前缀，因此可直接与管理后台服务端开发端口联调。

### 5.5 关键约束与注意事项

1. `scripts/genPageMap.js` 生成的 `src/utils/pageImports.ts` 是动态菜单可达的前置条件；该文件被忽略，不可直接执行不带生成步骤的构建或开发命令。
2. `package.json` 未定义通用 `build` 脚本。README 中若使用 `npm run build`，以及依赖该命令的 `deploy`、`preview`，当前可能失败；应明确使用 `build:zy` 或 `build:gj`，或补齐统一构建入口。
3. 后端菜单的 `component` 字段必须精确命中页面映射键；同时应确认菜单类型枚举与前端仅将特定类型识别为页面的逻辑一致。
4. 生产配置仍可能使用开发域名或预发布 API 前缀，发布前必须按实际环境复核 API、SSO、`PUBLIC_PATH`、静态资源与 SPA 回退配置。
5. token 当前存于 localStorage，需与 CSP、XSS 防护、过期续签、退出登录及重定向同源校验一并设计。

## 6. guard-find-backend：管理后台服务端

### 6.1 当前定位与结构

`guard-find-backend` 的技术架构、模块组织与 `guard-find-server` 高度相似，同样是 ContiNew Admin 多模块 Spring Boot 项目。它更适合作为 `guard-find-frontend` 的管理后台 API：提供用户、角色、菜单、组织、字典、租户、文件、日志、通知、调度、代码生成和开放平台等运营管理能力。

```text
guard-find-backend/
├─ continew-server/                     主后台 API、启动类、配置、迁移
├─ continew-system/                     auth 与 system 系统业务模块
├─ continew-common/                     通用 CRUD、上下文、异常、配置、工具
├─ continew-plugin/                     open / tenant / schedule / generator 插件
├─ continew-extension/                  独立 SnailJob 调度服务
├─ docker/                              MySQL、Redis、Nginx、服务容器编排
├─ .github/workflows/                   构建、部署、扫描、发版自动化
└─ pom.xml                              Maven 多模块 reactor 根
```

### 6.2 与管理前端的契约

| 前端行为 | 后端对应能力 |
| --- | --- |
| 登录并保存 Bearer Token | `POST /auth/login` |
| 加载当前用户及权限 | `GET /auth/user/info` |
| 加载后台动态菜单 | `GET /auth/user/route` |
| 前端请求自动加租户头 | 服务端读取 `X-Tenant-Id` / `X-Tenant-Code` |
| 401 后退出登录 | Sa-Token 会话失效或权限拒绝响应 |
| 通过动态菜单加载业务页面 | 菜单 path、component、type、权限码需与前端规则一致 |

### 6.3 重要代码职责

- `ContiNewAdminApplication`：Spring Boot 启动入口，启用 CRUD API、统一响应、文件存储、缓存、Feign 等能力。
- `SaTokenConfiguration`：登录拦截、开放 API 签名分流、密码过期控制及 CRUD 权限前缀缓存。
- `AuthServiceImpl`：客户端合法性校验、登录处理器分发、会话建立、角色菜单聚合和动态路由树生成。
- `BaseController` / `BaseServiceImpl`：为大量资源型接口复用 CRUD、权限推导、分页、导入导出和关联字段填充。
- `db.changelog-master.yaml`：通过 Liquibase 汇集系统和插件的 MySQL 初始化/升级脚本。

### 6.4 运行与部署

管理后台服务端的本地启动和打包方式与 `guard-find-server` 相同：准备 MySQL、Redis，配置 `DB_*`、`REDIS_*` 等参数后通过 IDE 运行主类或使用 Maven 构建。Docker Compose 中定义 MySQL、Redis、Nginx、主服务和 SnailJob 服务。

需要特别注意：默认 `dev` 端口也是 `8000`。因此用户服务端和管理后台服务端不能在同一台本地机器、同一端口上同时直接启动；联调时需要至少修改其中一个服务端口、使用不同 profile，或通过网关/容器端口映射隔离。

## 7. 跨项目协作约定建议

### 7.1 API 边界

建议明确两组 API 的域名或网关前缀，避免两个 Java 项目职责、端口、认证体系混用：

```text
用户应用：guard-find-app → guard-find-server
管理后台：guard-find-frontend → guard-find-backend
```

建议分别维护：

- 独立的 OpenAPI 文档、接口版本、错误码和变更记录；
- 用户端与管理端的认证客户端、角色权限、菜单与审计策略；
- 相互独立的数据库或至少清晰的 schema/表所有权；
- 独立的 Redis key 前缀、对象存储路径和调度任务命名空间；
- 开发、测试、预发布、生产环境的 API 基址与秘密配置。

### 7.2 领域模块建议

通用系统模块与 Guard Find 业务模块应显式隔离。例如在服务端建立业务根包/模块：

```text
<server-module>/src/main/java/.../guardfind/
├─ controller/       用户侧或后台侧 API
├─ service/          领域服务与事务编排
├─ mapper/           数据访问
├─ model/
│  ├─ entity/        持久化实体
│  ├─ req/           请求对象
│  ├─ query/         查询条件
│  └─ resp/          响应对象
└─ event/            可选：领域/集成事件
```

每项业务能力应同步包含：数据库 Liquibase 迁移、权限标识、接口文档、参数校验、日志/审计策略、前端页面及测试。

### 7.3 配置与安全

- 禁止在仓库、客户端包或前端构建产物中保留生产密码、JWT 密钥、RSA 私钥、云存储密钥、第三方 OAuth 密钥。
- 使用环境变量、部署平台 Secret 或密钥管理服务注入生产配置，并支持密钥轮换。
- 生产环境需关闭宽松 CORS、调试日志、开放 API 文档与开发代理；同时核验文件下载权限、对象存储公开策略与请求日志脱敏。
- 统一约定时间格式、分页参数、租户头、追踪 ID、错误响应结构和文件上传限制，避免 App 与管理后台客户端各自实现一套兼容逻辑。

## 8. 当前优先级建议

1. **确认架构边界**：明确 `guard-find-server` 和 `guard-find-backend` 是否需要保持两套独立部署、独立数据与独立认证客户端；若不需要，应尽早合并或提炼共享模块，降低重复维护。
2. **定义领域模型**：基于 Guard Find 实际业务建立用户侧与运营侧的领域表、Liquibase 迁移、服务接口、权限与审计规则。
3. **完成用户应用基础设施**：在 App 中增加环境配置、请求层、登录会话、错误边界、业务路由和响应式 UI。
4. **完成前后台联调契约**：核对 `/auth/login`、`/auth/user/info`、`/auth/user/route`、菜单 `component` 映射和租户头；补齐 OpenAPI 或契约测试。
5. **建立质量门禁**：为四个项目加入可一次性运行的类型检查、单元/集成测试和构建验证，避免依赖 watch 命令或默认跳过测试的构建流程。
6. **校准部署配置**：复核容器网络、端口、SnailJob 连通性、生产 API/SSO 域名、Nginx SPA 回退与跨域策略后再部署。

## 9. 本次审阅结论

- 四个项目的角色已具备清晰的预期划分：用户多端 App、用户服务端、管理前端、管理后端。
- 用户 App 已具备 Expo Web/移动端/HarmonyOS 的基础技术底座，但核心业务功能仍待实现。
- 管理后台前后端已具备较完整的通用 RBAC、动态菜单、租户与系统管理能力，但产品化前需清理模板残留并校准构建/部署配置。
- 两套服务端目前高度同构，且均未发现 Guard Find 专属领域实现；这是后续产品研发最重要的结构性待办。
